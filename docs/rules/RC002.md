# RC002: SECURITY DEFINER function callable by anyone

**Severity:** critical
**Standards:** CWE-269, CWE-862 · NIST SP 800-53 AC-3, AC-6 · CIS Controls v8 3.3, 6.8

## What it catches

A `SECURITY DEFINER` function in an exposed schema that `PUBLIC` or `anon` can execute.

## Why it matters

A `SECURITY DEFINER` function runs with its owner's powers, which usually means it skips row-level security entirely. That's often the point: a helper that fetches one customer's data on their behalf.

But Postgres grants `EXECUTE` on every new function to `PUBLIC` by default, and Supabase's stock setup also grants it to `anon` and `authenticated`. Unless you revoke that, anyone with your public key can call the function through `/rest/v1/rpc/...` and pass in any argument they like, such as another customer's id.

rattlecheck tracks grants in order. Dropping and re-creating a function resets its grants, so a revoke written before the re-create no longer counts. `CREATE OR REPLACE` keeps them. Overloads are tracked separately: revoking `f(uuid)` does not protect `f(uuid, text)`.

## How to fix

```sql
revoke execute on function public.your_function(uuid) from public, anon;
-- Only if signed-in users should be able to call it:
grant execute on function public.your_function(uuid) to authenticated;
```

To make every new function start closed:

```sql
alter default privileges revoke execute on functions from public;
alter default privileges in schema public revoke execute on functions from anon, authenticated;
```

## Allowing it

Some functions really are meant for the public, like a store locator. Add them to `rattlecheck.config.json` with a reason, and make sure the function only returns data that's safe for anyone to see.
