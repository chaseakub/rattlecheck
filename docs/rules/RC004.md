# RC004: Invoker-rights trigger writes to a table locked to the server

**Severity:** high
**Standards:** CWE-279 · NIST SP 800-53 AC-6, AU-9 · CIS Controls v8 8.2

## What it catches

A trigger function that runs with the caller's rights (`SECURITY INVOKER`, the default) and writes to a table that has row-level security on and no policies.

## Why it matters

RLS on with no policies is a legitimate way to lock a table to your server: perfect for an audit log. But a trigger that writes to it on a user's behalf runs as that user. The insert is denied with `42501`, and Postgres rolls back the user's whole change.

This one hides well. Server jobs and cron tasks use the service role, which bypasses RLS, so every pipeline keeps working and every health check stays green. Only real users fail, and only on the actions that fire the trigger. In the incident behind this rule, saves failed for every user for seven days before anyone noticed.

## How to fix

```sql
alter function public.your_trigger_fn() security definer;
alter function public.your_trigger_fn() set search_path = '';
```

Trigger functions can't be called directly, so making them `SECURITY DEFINER` doesn't open a new door. It's also the right design for audit tables: an audit trail shouldn't depend on the permissions of the person it's auditing, and a policy that lets users insert into it would let them forge entries.
