# RC006 · Anonymous SELECT includes private columns

A public directory can list every studio's name while keeping its billing email private. PostgreSQL uses row policies to decide which records a visitor can see and privileges to decide which fields the visitor can read.

RattleCheck replays grants to `anon` and `PUBLIC` separately, including table-wide defaults and named column grants. It checks RLS-enabled tables in exposed schemas with a SELECT or ALL policy applicable to signed-out visitors. It reports permission on visible rows. A static check cannot prove which records a policy actually returns.

| Finding | Severity |
| --- | --- |
| A readable field is designated private in config, starts with `private_` or `internal_`, or has a recognized credential or identifier name such as `password_hash`, `api_key`, or `ssn` | High |
| A readable field is named `email` or `email_address` | Warning. A public contact address can be intentional. |
| A public row policy permits unrestricted reads and SELECT covers the whole table | Warning. Adding a column also grants anonymous read access to it. |

Camel-case equivalents such as `privateEmail` are also checked. Add domain-specific names to your config. Column names in config match PostgreSQL's stored case.

```json
{"privateColumns":{"public.directory":["draft_budget"]}}
```

[See the before-and-after example in your browser.](https://chaseakub.github.io/rattlecheck/column-permissions/)

## Keep the rows public and restrict the fields

For the [directory example](../../examples/public-directory), the broad grant is `GRANT SELECT ON public.directory TO anon`. The intended public fields are `id` and `display_name`. Keep the row policy and apply this migration:

```sql
revoke select on public.directory from public, anon;
grant select (id, display_name) on public.directory to anon;
```

A second, narrower grant alone leaves the original wide grant in place. Revoking a single column also leaves a table-level grant intact. After narrowing access, clients should select the public fields explicitly.

An RC005 exception for intentional public rows leaves RC006 active. A field-specific RC006 exception applies to that field only. The scanner models direct grants and the built-in PUBLIC role. Custom role memberships, columns inferred from queries or inheritance, dashboard changes, and arbitrary business sensitivity require additional review.

The [PostgreSQL test](../../examples/public-directory/verify.psql) uses a fictional directory entry and the same two migrations. It checks that the public fields still load and that reading the private email then raises a permission error.
