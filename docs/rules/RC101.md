# RC101: Live table hands rows to the public key

**Severity:** critical
**Runs with:** `--live`
**Standards:** CWE-200, CWE-284 · NIST SP 800-53 AC-3, AC-6 · CIS Controls v8 3.3

## What it catches

A table on your running project that returns one or more rows to a request carrying only the public (anon or publishable) key.

## Why it matters

Migrations describe what your database should be. The live check asks what it actually is. It catches a policy someone added in the dashboard, a table changed by hand, or anything inside dynamic SQL a static reader can't see. When your migrations say a table is locked and the live project hands out rows anyway, rattlecheck says so.

## How it checks, and what it won't do

- It only runs after proving you own the project (a Supabase access token that can see it, or the project's service key).
- Each table gets one `HEAD` request with `Prefer: count=exact`. The server answers with a count. No rows are downloaded, nothing is written, nothing is stored.
- Keys are only sent to `https://<project-ref>.supabase.co` or a local Supabase, and no request follows a redirect.
- A count of zero is reported as "locked or empty". From outside, those look the same.

## How to fix

Turn on row-level security for the table and review its policies:

```sql
alter table public.your_table enable row level security;
```

If the data is meant to be public, allow it in `rattlecheck.config.json` with a reason.
