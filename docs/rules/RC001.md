# RC001: Table reachable through the API without row-level security

**Severity:** critical
**Standards:** CWE-284, CWE-862 · NIST SP 800-53 AC-3, AC-6 · CIS Controls v8 3.3

## What it catches

A table in an exposed schema (usually `public`) that `anon` or `authenticated` can reach, with row-level security (RLS) turned off. That includes tables created as a copy with `CREATE TABLE ... AS SELECT`.

## Why it matters

Supabase serves every table in an exposed schema over HTTP. The key that lets your website talk to it ships inside your website's code, so anyone can copy it. With RLS off, that key can read and change every row.

Copies are the sneaky case. `create table backup as select * from customers` copies the rows and none of the security: no RLS, no policies, and Supabase's default grants to `anon` and `authenticated`. A backup made before a risky change can quietly become the one table on your project anyone can read.

## How to fix

```sql
alter table public.your_table enable row level security;
```

With RLS on and no policies, only your server (the service role) can use the table. Then add a policy for each thing users should be allowed to do:

```sql
create policy "read own rows" on public.your_table
  for select to authenticated
  using ((select auth.uid()) = user_id);
```

For a copy you only needed briefly, lock it and drop it when you're done:

```sql
alter table public.your_copy enable row level security;
revoke all on public.your_copy from anon, authenticated;
```

## Not a finding

- Tables where you revoked every privilege from `anon` and `authenticated`.
- Tables in schemas the API doesn't expose.
